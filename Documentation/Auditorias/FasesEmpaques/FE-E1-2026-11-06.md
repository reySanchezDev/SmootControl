## Casos RPC ejecutados en el laboratorio

Se invocó `public.pos_sync_sale` con dos dispositivos sintéticos, cajas locales
abiertas y reglas de empaques sintéticas. Los resultados observados fueron:

| Caso | Resultado | Evidencia resumida |
| --- | --- | --- |
| Para llevar con regla y `tracks_stock=true` | PASS | Descuento de una unidad y movimiento `packaging_sale` |
| Delivery con regla y `tracks_stock=false` | PASS | Movimiento registrado, sin stock material que descontar |
| Comer aquí con regla | PASS en cobertura local | Cubierto por prueba de repositorio; la RPC local también respetó la regla |
| Comer aquí sin regla | PASS | No se creó movimiento |
| Para llevar sin regla | PASS | No se creó movimiento |
| Stock insuficiente | PASS | RPC rechazó; no quedaron fila de venta ni movimiento parcial |
| Reenvío de venta | PASS | Mismo movimiento lógico, sin duplicación; saldo estable |
| Dos terminales sintéticas | PASS parcial | Ventas quedaron asociadas a dispositivos distintos; no certifica concurrencia simultánea |

Las pruebas locales de Ventas comprobaron además anulación y reintegro de stock
en Drift. La prueba remota de anulación por `pos_sync_sale` quedó bloqueada por
una incompatibilidad comprobada: la función intenta insertar `sale_voids` sin
los campos ahora obligatorios `original_total_amount` y relacionados. PostgreSQL
rechazó la operación con `null value in column "original_total_amount" ...
violates not-null constraint`. La transacción se revirtió y no se modificó la
venta ni su stock. No se modificó la migración ni se ocultó el defecto.
